# Theoretical Foundation: Why RDTL is Context-Free

## The Problem with Unrestricted HTML + Django Templates

### HTML5 Parsing is Context-Sensitive

Standard HTML5 parsing is **not** context-free because:

1. **Implicit Tag Closing**: Tags like `<p>` can be implicitly closed by other tags
   ```html
   <p>First paragraph
   <p>Second paragraph
   ```
   This requires the parser to "know" that a `<p>` inside another `<p>` implicitly closes the first.

2. **Optional Closing Tags**: Some tags can be left unclosed
   ```html
   <ul>
   <li>Item 1
   <li>Item 2
   </ul>
   ```

3. **Context-Dependent Parsing**: The same text can mean different things in different contexts
   ```html
   <script>var x = "<div>";</script>  <!-- Not an HTML tag -->
   <div>Text</div>                    <!-- HTML tag -->
   ```

### Django Templates Add More Complexity

Django templates introduce additional challenges:

1. **Template Syntax in Attributes with Same Quote Type**:
   ```html
   <div class="{% if x == "y" %}active{% endif %}">
   ```
   This requires context tracking to handle nested quotes of the same type.

   **RDTL Solution**: Allow templates in attributes, but enforce opposite quote rule:
   - Double-quoted attributes → use single quotes in templates
   - Single-quoted attributes → use double quotes in templates

   This maintains CFG by using a simple state (attribute opening quote) to determine allowed quotes inside.

2. **Interleaved Nesting**:
   ```html
   <div>
   {% if condition %}
   </div>
   {% endif %}
   ```
   Template blocks can span across HTML boundaries.

3. **Variable Resolution**: `{{ user.name }}` requires runtime context.

These features require the parser to maintain **context** beyond what a pushdown automaton (PDA) can handle with a simple stack.

## How RDTL Achieves Context-Freedom

### Restriction 1: Strict HTML with LIFO Nesting

**Rule**: All HTML tags must close in Last-In-First-Out order.

```
✓ Valid:   <div><p>text</p></div>
✗ Invalid: <div><p>text</div></p>
```

**Why this helps**:
- Eliminates need for implicit closing rules
- Parser can use a simple stack to track open tags
- No lookahead beyond current token needed

**Grammar production**:
```ebnf
HtmlElement = OpenTag Element* CloseTag
```

This is a standard context-free production. The parser pushes `OpenTag` onto the stack and pops when it sees the matching `CloseTag`.

### Restriction 2: No Template Syntax in HTML Tags

**Rule**: Template variables and tags cannot appear in HTML tag syntax.

```
✗ Invalid: <div class="{{ class_name }}">
✗ Invalid: <{{ tag_name }}>
✗ Invalid: <div {% if x %}data-x="1"{% endif %}>
```

**Why this helps**:
- HTML tags and template syntax are **disjoint** at the lexical level
- Lexer can tokenize without maintaining state about "am I in a tag?"
- Clear separation between HTML and template namespaces

**Lexical grammar**:
```
HtmlOpenTag  = '<' Identifier Attribute* '>'
TemplateVar  = '{{' Expression '}}'
TemplateTag  = '{%' Statement '%}'
```

These patterns are mutually exclusive - no ambiguity.

### Restriction 3: Template Blocks Respect HTML Boundaries

**Rule**: Template control structures must be properly nested with HTML.

```
✓ Valid:
<div>
  {% if x %}
    <p>Text</p>
  {% endif %}
</div>

✗ Invalid:
<div>
  {% if x %}
</div>
  {% endif %}
```

**Why this helps**:
- Both HTML and template blocks follow the **matched parentheses** property
- Can verify correctness with a single stack
- No need to track which context we're in

**Grammar production**:
```ebnf
Element = HtmlElement | TemplateBlock | Variable | Text

TemplateBlock = IfBlock | ForBlock | BlockTag

IfBlock = IF_OPEN Element* ELIF_OPEN Element* ELSE_OPEN Element* IF_CLOSE
```

The key insight: `Element*` can contain either HTML or more template blocks, and they nest properly.

### Restriction 4: Whitelisted Template Tags

**Rule**: Only a fixed set of template tags are allowed.

**Why this helps**:
- Finite number of productions in the grammar
- No dynamic tag creation
- Parser generator can create a complete parse table

## Proof Sketch: RDTL is Context-Free

### Theorem
RDTL (Restricted Django Template Language) with strict HTML can be recognized by a pushdown automaton and generated by a context-free grammar.

### Proof Sketch

1. **Lexical Analysis is Regular**
   - All tokens (`<tag>`, `{%`, `{{`, etc.) can be recognized by a finite automaton
   - Token boundaries are unambiguous (restriction 2)
   - Therefore, lexing is regular and produces a token stream

2. **Syntax is Recognizable by PDA**
   - Define a PDA with stack alphabet: {HTML tag names, Template block types}
   - On `<tag>`: push `tag` onto stack
   - On `</tag>`: pop stack if top is `tag`, else reject
   - On `{% if %}`: push `if` onto stack
   - On `{% endif %}`: pop stack if top is `if`, else reject
   - Similar for other template blocks

3. **Grammar Productions are Context-Free**
   Each production has the form: `A → α` where `A` is a non-terminal and `α` is a string of terminals and non-terminals.

   Examples:
   ```
   Document → Element*
   Element → HtmlElement | TemplateBlock | Variable | Text
   HtmlElement → OpenTag Element* CloseTag
   TemplateBlock → IfBlock | ForBlock | ...
   IfBlock → IF_OPEN Element* IF_CLOSE
   ```

   All productions are context-free (no context requirements like "A → α in context C only").

4. **Proper Nesting Ensures Deterministic Parsing**
   - Restriction 3 ensures that template and HTML nesting is **matched**
   - This is equivalent to the Dyck language (matched parentheses), which is context-free
   - LR(1) parser can be constructed without conflicts

### Comparison to Full Django Templates

| Feature | Full Django | RDTL | Consequence |
|---------|-------------|------|-------------|
| Template in attributes | ✓ (any quotes) | ✓ (opposite quote rule) | Maintains CFG with simple state |
| Implicit HTML closing | ✓ | ✗ | Enables LIFO stack parsing |
| Interleaved nesting | ✓ | ✗ | Ensures matched structure |
| Dynamic tag loading | ✓ | ✗ | Finite grammar |
| Arbitrary Python expressions | ✓ | Limited | Prevents undecidability |

## Practical Implications

### What You Gain

1. **Fast, Predictable Parsing**
   - Linear time complexity: O(n) where n is input length
   - No backtracking or ambiguity resolution
   - Efficient parser generators (yacc, ANTLR, etc.) can be used

2. **Better Error Messages**
   - Exact line/column of syntax errors
   - Clear expectations about what should come next
   - Pre-parse validation catches errors before parsing

3. **Static Analysis**
   - Can build AST without executing code
   - Template linting and type checking possible
   - Security analysis (XSS detection) easier

4. **Editor Support**
   - Syntax highlighting with no false positives
   - Accurate auto-completion
   - Code folding based on structure

### What You Lose

1. **Dynamic Attributes**
   ```html
   <!-- Not allowed in RDTL -->
   <div class="{% if active %}active{% endif %}">
   ```

   **Workaround**: Use full element duplication
   ```html
   <!-- RDTL version -->
   {% if active %}
     <div class="active">Content</div>
   {% else %}
     <div>Content</div>
   {% endif %}
   ```

2. **Flexibility**
   - Must write more verbose templates
   - Some Django template features not supported

3. **HTML5 Lenience**
   - Must close all tags explicitly
   - Stricter than browser HTML parsing

## Conclusion

RDTL achieves context-free parsing by:

1. **Lexical disjointness**: Template syntax never appears in HTML syntax
2. **Strict nesting**: Both HTML and templates follow LIFO stack discipline
3. **No context-dependent rules**: Every production is purely syntactic
4. **Finite grammar**: Fixed set of template tags and HTML rules

This makes RDTL suitable for:
- Static analysis tools
- Fast template engines
- Security-critical applications
- Educational purposes (teaching parsing theory)

The trade-off is verbosity for verifiability - a worthwhile exchange in many contexts.
